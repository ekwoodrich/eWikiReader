---
name: ewikireader-release
description: Create and verify an eWikiReader stable release through a labeled dev-to-main pull request, including signed APK and generated changelog validation.
---

Read root `AGENTS.md` and `docs/workflow-plan-v1.md`. A release request authorizes the normal PR/merge/publication steps; a request only to prepare a PR does not authorize merging it.

1. Fetch branches/tags, inspect the working tree and open PRs, and ensure intended work is committed on `dev`. Incorporate `origin/main` into `dev` if needed; preserve unrelated work. Review the entire `origin/main...dev` diff. Do not publish local feature work directly from `main`.
2. Choose the requested release mode. For a new release, default to patch when unspecified and use one label: `release:patch`, `release:minor`, or `release:major` (`release` also means patch). For a corrective rebuild of the latest stable release at the same version, use `release:replace` or append `:replace` to the selected release label. Replacement rebuilds the latest stable version, migrates its tag to `vMAJOR.MINOR.PATCH-release`, refreshes that changelog section, and deletes/recreates that GitHub Release only after the signed APK builds successfully. Determine versions from `-release` tags and historical unsuffixed/`-eink` tags; ignore `dev-*` prereleases and other tag formats.
3. Push `dev`, create/reuse a PR with base `main`, head `dev`, and the chosen label **before merge**. Use a concise body file describing changes and verification. Check CI; when authorized, merge with `gh pr merge --merge`. Avoid squash/rebase, which discard dev ancestry and undermine commit-count version ordering.
4. Monitor the `Signed Build & Publish` run for that PR (`release.yml`). Build/signing must succeed before the workflow creates and merges its bot-authored changelog PR, updates tags, or publishes. If it fails, inspect logs without exposing credentials, fix on a feature branch through `dev`, and avoid blindly rerunning after partial publication: first inspect any changelog PR/merge, existing tags, and releases.
5. Verify the expected `vX.Y.Z-release` stable tag, `vX.Y.Z` title, clean APK filename, latest-release status, generated `CHANGELOG.md` and release notes, and uploaded APK. Download the actual asset, verify it with `apksigner`, inspect package/version using `aapt2 dump badging` or `apkanalyzer`, and compare its SHA-256 checksum with the GitHub asset digest. Package must be `io.github.ekwoodrich.ewikireader`; release certificate must stay consistent with prior signed artifacts. A Play Protect scan is separate from signature verification.
6. Fetch/pull the bot's changelog commit on `main` and merge `origin/main` back into `dev` (fast-forward if possible). Push within the release request's scope, leave task changes clean, and report PR, run, release URL, version, and validation limits.
